# 01 — المعمارية (Core Architecture)

**الحالة: مُجمَّدة (Architecture Freeze).** أي تعديل يحتاج سببًا هندسيًا حقيقيًا يظهر أثناء التنفيذ، ويُعرَض للموافقة قبل التنفيذ — راجع `03_RULES.md` لبروتوكول التعديل.

## 1) نموذج الطبقات الأربع

```
البوتات (+ لوحة ويب/API مستقبلًا)
        ↓ يستدعي فقط
CipherKeep Core  ← كل منطق الأعمال
        ↓ يستدعي فقط
Data Access Layer  ← وصول قاعدة بيانات فقط
        ↓
Supabase (التخزين الدائم)
```

**قاعدة صارمة:** كل طبقة تستدعي فقط الطبقة التي تحتها مباشرة. البوت ممنوع يوصل DAL مباشرة.

## 2) مسؤوليات كل طبقة

| الطبقة | تحتوي | ممنوع عليها |
|---|---|---|
| **البوتات/الواجهات** | استقبال الطلب، تحليل الهوية الخاصة بقناتها، استدعاء Core، عرض النتيجة بشكل قناتها | أي قرار عمل، أي منطق تحقق أو تشفير |
| **CipherKeep Core** | كل منطق الأعمال: إنشاء كود، تحقق، إدارة أجهزة، سياسات صلاحية | استيراد تيليجرام، SQL خام، معرفة قناة الاتصال (تتعامل بمعرّف مستخدم داخلي مجرَّد فقط) |
| **Data Access Layer** | استعلامات Supabase فقط، تنفيذ فعلي لواجهات Core المجرَّدة | أي قرار عمل أو قاعدة صلاحية |
| **Supabase** | التخزين الدائم، تشفير `key_material` عبر pgcrypto | — |

**تحليل الهوية:** تحويل `telegram_id` خام لمعرّف مستخدم داخلي = مسؤولية البوت. القرار "هل هذا الدور مخوَّل" = مسؤولية Core حصرًا.

## 3) مبدأ عكس التبعية (Dependency Inversion)

Core يعتمد على واجهات مجرَّدة (`CodeRepository`, `DeviceRepository`، عبر `typing.Protocol`، بلا `ABC` أو إطار حقن تبعيات) — لا يعرف Supabase مباشرة.

**السبب المعتمد: قابلية الاختبار** (لا "تبديل قاعدة بيانات مستقبلي" — تبرير مرفوض لغياب أي مؤشر حقيقي عليه). يمكّن اختبار Core بمعزل تام عن اتصال شبكي، عبر تنفيذات وهمية بالذاكرة.

**قرار مرتبط:** لا يوجد `LicenseRepository` منفصل — الكود هو الترخيص نفسه بالمرحلة الحالية. `CodeRepository` واحدة تكفي. يُعاد فتح هذا فقط لو ظهرت حاجة فعلية (ترخيص واحد يغطي عدة أكواد).

## 4) خدمات المجال (Domain Services) — لا تضخيم على Core

عمليات مركّبة خاصة بنمط معيّن (مثل فك تشفير وضع السيرفر) **لا تُضاف كدوال جديدة على `CipherKeepCore`** — هذا يخلق تضخمًا تدريجيًا مع كل عملية جديدة.

**البديل:** صنف خدمة منفصل يعتمد على `CipherKeepCore` **بالتركيب (Composition)**، لا التعديل عليه.

**مثال منفَّذ:** `ServerModeService` — يستدعي `verify_code`، يضيف فوقها فك التشفير (`crypto.py`، موديول تشفير خالص، بلا منطق أعمال). `CipherKeepCore` نفسه بقي بلا أي تعديل أو تبعية جديدة (مؤكَّد بفحص مباشر للملف).

أي عملية مركّبة مستقبلية (مثل `/admin/decrypt`) تتبع نفس النمط: خدمة جديدة منفصلة، لا تعديل على Core.

## 5) سياسة Transaction / Concurrency

**المشكلة:** تسلسل "قراءة → عدّ → تسجيل" لحجز سلوت جهاز غير ذري — Race Condition حقيقية بين طلبات متزامنة.

**القرار:** التزامن الحقيقي بين طلبات HTTP مستقلة لا يُحَل بكود بايثون أو داخل Core — لا ذاكرة مشتركة تمنع التداخل. الذرّية مسؤولية محرك التخزين حصرًا.

**التنفيذ:** دالة SQL/RPC واحدة (`ck_claim_device_slot`)، تقفل صف الكود (`FOR UPDATE`) طوال الفحص والتسجيل معًا. لا Core ولا DAL يحملان أي منطق قفل.

**تمييز مهم:** ليست كل `verify_code` ذرية بالضرورة — قراءة حالة الكود (ملغى/منتهي) قراءة عادية غير حرجة (تأخير بسيط مقبول). فحص-ثم-تسجيل الجهاز **تحديدًا** هو ما يحتاج ذرّية صارمة (لأن التداخل هنا يقلب نتيجة صحيحة لخاطئة).

**حدود منطق SQL:** دالة RPC تقرأ `max_devices` من جدول `codes` كجزء من عمليتها الذرية — هذا قراءة قيمة مُهيَّأة مسبقًا من Core، لا قرار عمل جديد. الحد الأدنى الحقيقي، لا يمكن تقليصه أكثر بدون كسر الذرّية.

**العقد:** `DeviceRepository.claim_device_slot()` — دالة ذرية واحدة، ترجّع `DeviceClaimStatus` (Enum: `REGISTERED` / `ALREADY_REGISTERED` / `LIMIT_REACHED`)، لا نصوصًا حرة.

**خطر متبقٍّ غير محلول (مُقَرّ به):** فشل شبكي بعد تنفيذ RPC فعليًا لكن قبل وصول الرد للعميل (مشكلة Idempotency). متطلب تصميم مستقبلي، لا معالجة إضافية بهذي المرحلة.

## 6) بصمة الجهاز (Device Fingerprint)

بصمة الجهاز على أندرويد/Termux ضعيفة وقابلة للتزييف نسبيًا. **القرار:** تُعامَل دائمًا كـ"إشارة بأفضل جهد" (best-effort) — **ممنوع معماريًا** ربط أي إجراء لا رجعة فيه (حظر دائم، اتهام احتيال) بها منفردة.

## 7) معيار إدراج الحقول المبكر بقاعدة البيانات

لا إدراج حقل/علاقة/جدول إلا بتحقق أحد الشرطين:
- **شرط أ:** فقدان معلومة لا رجعة فيه لو غاب الحقل الآن.
- **شرط ب:** تكلفة تعديل كاسرة فعليًا لو أُضيف لاحقًا.

كل ما دون ذلك → `06_TODO.md` (Backlog). مثال مرفوض فعليًا: `moderator_id` بجدول `codes` (كل السجلات فارغة القيمة بالمرحلة الحالية، لا يجتاز أي شرط).

## 8) حل مشكلة فقدان البيانات (نظام الملفات المؤقت)

**المشكلة الأصلية:** Render (المجاني) نظام ملفات مؤقت — أي بيانات محلية تُمسح مع كل إعادة نشر. أكواد العملاء ومفاتيح وضع السيرفر كانت تضيع للأبد مع كل تحديث.

**القرار:** Supabase (Postgres) = المصدر الوحيد للحقيقة لكل حالة دائمة، لكل المكوّنات دون استثناء.

**قرار مُلغى صراحة:** طبقة نسخ احتياطي تلقائي لتيليجرام — اقتُرحت كحل احتياطي، أُلغيت لأن Supabase حل المشكلة جذريًا؛ نسخ احتياطي إضافي فوق حل جذري لا يبرر نفسه بهذي المرحلة.

## 9) حدود Phase 1 الحالية

مصدر الحقيقة الموحَّد ينطبق حاليًا على **`/verify` و`/admin/create` فقط**. نقاط الإدارة الأخرى (`/admin/revoke`, `/admin/extend`, `/admin/pause_all`, `/admin/list`) ما زالت تعتمد على `licenses.json` المحلي مؤقتًا — مصدرا حقيقة منفصلان حاليًا لأنواع عمليات مختلفة، بقرار واعٍ لا سهو، بانتظار ترحيل مستقل لاحقًا (`06_TODO.md`).
