# 00 — رؤية المشروع (Vision)

## الهوية النهائية
CipherKeep منصة تجارية طويلة المدى لحماية أدوات المطورين وإدارة التراخيص، فيها ثلاثة أدوار: **مالك**، **مشرفون**، **عملاء**. تبدأ ببوتات تيليجرام، وتتوسع مستقبلًا لتشمل لوحة ويب وAPI عام.

الهدف ليس "بوت يشتغل"، بل مشروع بجودة هندسية يمكن الاعتماد عليه والتوسع فيه لسنوات.

## فلسفة التنفيذ: Vision مقابل Roadmap
- **Vision (هذا الملف):** لا تُحذف ولا تُقلَّص أبدًا. تمثّل الطموح الكامل للمشروع.
- **Roadmap (`02_ROADMAP.md`):** ينفّذ فقط ما يحتاجه الإصدار الحالي. أي ميزة من الرؤية غير مطلوبة الآن تُنقل لـ`06_TODO.md` (Backlog) — **محفوظة، لا محذوفة**.

القاعدة: لا نصمم القمة قبل الأساس. الطبقة الأساسية تُبنى وتُثبَّت أولًا، والنمو يصير طبقة فوق طبقة على أساس شغّال فعليًا — لا على تصميم نظري متراكم.

## فلسفة التصميم — لماذا Core / DAL / Adapter

المشكلة الأصلية: منطق الأعمال كان مكتوبًا داخل البوتات مباشرة. أول ما ظهرت فكرة لوحة ويب/API عام مستقبلًا، تبيّن إن أي منطق داخل بوت واحد سيحتاج تكرارًا لكل واجهة جديدة.

الحل: فصل ثلاثي —
- **البوتات/الواجهات:** نقل فقط (Transport). لا تعرف شيئًا عن قرارات العمل.
- **CipherKeep Core:** كل منطق الأعمال، بمعزل تام عن أي تقنية خارجية (تيليجرام، Supabase).
- **Data Access Layer:** تنفيذ فعلي لتخزين البيانات، بأمر من Core فقط.

تفاصيل كل طبقة ومسؤولياتها الدقيقة موثّقة بـ`01_ARCHITECTURE.md`.

## المبدأ الأهم عبر كل قرار
كل إضافة (حقل، جدول، تجريد، ميزة) يجب أن تُبرَّر بحاجة فعلية حالية أو تكلفة تعديل كاسرة لاحقًا — لا "قد نحتاجها مستقبلًا". هذا المبدأ مطبَّق حرفيًا على كل قرار موثَّق بـ`05_DECISIONS.md`.
