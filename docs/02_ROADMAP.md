# 02 — خطة التنفيذ (Roadmap)

للحالة اللحظية التفصيلية لكل خطوة، راجع `04_PROGRESS.md`. هذا الملف يوثّق **الخطة الثابتة**، لا يتكرر تحديثه مع كل تقدّم.

## Phase 1 — الهدف
إثبات صحة المعمارية (`01_ARCHITECTURE.md`) بأصغر شريحة عمل حقيقية. النطاق محصور بجدولي `codes` و`devices`، طبقة Core + DIP، وبوت التشفير كعميل خفيف.

## نطاق Phase 1 (داخل الحدود)

1. مخطط قاعدة بيانات Supabase (`codes`, `devices` + `pgcrypto`)
2. `CipherKeep Core` (حزمة بايثون مستوردة مباشرة، لا خدمة شبكية) + الواجهات المجرَّدة + تنفيذ وهمي للاختبار + اختبارات وحدة
3. Data Access Layer فعلي ضد Supabase حقيقية + اختبار تكامل
4. ترحيل `/verify` و`/admin/create` لاستخدام Core، تقاعد التخزين المحلي لهذين المسارين تحديدًا
5. إصلاح بوت التشفير (وضع السيرفر يستدعي `Core.create_code` بمعاملات `trial`/`max_devices`/`expire_days` فعلية، لا قيم ثابتة)
6. فحص صحة عند الإقلاع لكل سيرفر، تنبيه فوري عند فشل الاتصال بقاعدة البيانات
7. إثبات حي شامل: إنشاء كود → تشفير ملف فعلي → تحقق ناجح → محاكاة إعادة نشر → تحقق ناجح مرة أخرى بلا فقدان بيانات

## خارج نطاق Phase 1 صراحة (Backlog، محفوظ لا محذوف)

نظام المشرفين والباقات، الاستئناف/طلبات المراجعة، المساعد الذكي، بوت الدعم، تعدد اللغات، Mini Apps، لوحة الويب، الخرائط الحرارية، كشف الاحتيال الجغرافي، ترحيل `/admin/revoke`/`/admin/extend`/`/admin/pause_all`/`/admin/list`. التفاصيل الكاملة بـ`06_TODO.md`.

## ترتيب البناء التالي (بعد Phase 1)

1. بوت الإدارة + قاعدة بيانات موسَّعة (مشرفون، باقات) — يبني فوق نفس Supabase
2. بوت الدعم/العملاء — يعتمد على بيانات البقية
3. مراجعة أمن سيبراني شاملة بعد اكتمال البوتات الثلاثة، وربطها النهائي

## بروتوكول العمل بين مراحل التطوير

كل خطوة تُنفَّذ فقط بعد إذن صريح ("ابدأ") بنفس المحادثة. القرارات المعمارية أو تعديلات العقود التي تظهر أثناء التنفيذ تُعرَض للموافقة قبل التنفيذ (`03_RULES.md`). لا توسيع نطاق خطوة بميزة جديدة أثناء تنفيذها.
